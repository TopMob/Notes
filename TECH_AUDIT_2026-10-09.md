## P0: угрозы данным

### A01. Инициализация может удалить все заметки

**Источник:** `src/db/storage.ts:20–45`.

При наличии хотя бы одного блокнота `nb-college` `initStorage()` очищает notebooks, sections, pages, strokes, shapes и textBlocks, включая любые другие пользовательские блокноты. Это автоматическая ветка загрузки приложения, без резервной копии и подтверждения. Условие применимо к базе, содержащей этот старый идентификатор; наличие его у пользователя не проверялось.

**Воспроизведено:** при заглушке с двумя блокнотами `nb-college` и `real-notebook` вызваны `clear()` всех шести таблиц.

**Направление исправления:** убрать автоматическую массовую очистку; любые миграции выполнять с проверкой структуры, сохранением исходных данных и возможностью восстановления.

### A02. Turso-токен передаётся браузеру, граница безопасности находится в клиенте

**Источник:** `src/services/sync/tursoProvider.ts:20–30`.

`VITE_TURSO_AUTH_TOKEN` используется непосредственно в браузерном libSQL-клиенте. При размещении обычного общего токена с правом записи в этой переменной посетитель получает эти права независимо от Clerk и может выполнять запросы вне фильтров приложения. Конкретный production-токен и его ограничения не проверялись: критичность зависит от выданных ему прав и области доступа.

Дополнительно `ON CONFLICT(id)` в Turso обновляет записи без проверки владельца, а начальные ID (`nb-my-notebook`, `sec-quick-notes`, `page-default`) одинаковы у всех пользователей. Для общей базы это реальный путь конфликтов между аккаунтами. В Supabase тот же глобальный ключ может приводить к отказам записи под RLS. Исправлять существующие ID массовым переименованием без плана миграции нельзя.

**Направление исправления:** доверенный серверный шлюз с проверкой Clerk и владельца либо действительно изолированные базы/ограниченные полномочия. При необходимости — отзыв ранее опубликованного общего токена после подготовки замены. Секретные значения во время аудита не читались и не выводились.

Vite прямо описывает, что значения `VITE_*` входят в клиентскую сборку: [документация Vite](https://vite.dev/guide/env-and-mode).

## P1: синхронизация и локальная надёжность

### A03. Ошибка IndexedDB теряет очередь и отображается как успешное сохранение

**Источник:** `src/store/useCanvasStore.ts:165–239`.

`pageDirtyMap.delete(pageId)` происходит до записи. При ошибке diff не возвращается в очередь, ошибка подавляется, а `finally` ставит `saveStatus: 'saved'`. Повторное сохранение без новых изменений ничего не делает. При переключении страницы или перезагрузке изменения, оставшиеся только в памяти, могут пропасть. `AssetManager.saveAsset()` также подавляет ошибку записи изображения и возвращает успешный результат.

**Воспроизведено:** ошибка `savePageDiff()` с сообщением simulated QuotaExceededError; после двух вызовов flush — одна попытка записи, статус saved, dirtyStillQueued=false.

**Направление исправления:** восстанавливать diff при ошибке с сохранением более новых правок, показывать честный статус, не продолжать опасное переключение как будто запись успешна. Сохранение изображения должно сообщать о неперсистентном результате.

### A04. PUSH и PULL одной синхронизации используют несовместимые снимки

**Источник:** `src/services/sync/syncEngine.ts:304–310, 368–413, 506–536`.

`cloudData` загружается до PUSH. После отправки новых локальных элементов PULL без проверки версии записывает старые элементы из этого исходного облачного снимка через `put(el.data)`.

**Воспроизведено:** локальный штрих s имеет color=new и страница updatedAt=300, облачный s — color=old и updatedAt=100. После `syncAll()` локальный штрих получает color=old, хотя локальная страница отправлялась в облако.

Разница названий дополнительно считается основанием PUSH даже при более новой облачной версии. Старое локальное название отправляется поверх нового облачного, а локально затем принимается старый снимок ответа. Клиенты могут расходиться и повторно перетирать названия.

**Воспроизведено:** local title=old/100, cloud title=new/300; pushPages получает old.

**Направление исправления:** явные версии/ревизии и политика конфликтов, проверка базовой версии при записи, запрет применять устаревший PULL поверх локальных правок. При конфликте сохранять обе версии. Простая перестановка PUSH/PULL сама по себе проблему одновременных правок не решает.

### A05. Удаления элементов не передаются как удаления

**Источник:** оба провайдера, `pushPageElements()`/`pullAll()`; `syncEngine.ts:506–536`.

Облако получает полный бандл страницы. На чтении бандл разворачивается в отдельные элементы, а локальный PULL выполняет только put/delete присутствующих элементов. Элемент, отсутствующий в новом бандле, не получает tombstone и не удаляется локально. Пустой бандл вообще теряет идентичность снимка и его версию после разворачивания.

**Воспроизведено:** в локальной БД есть штрих deleted, облачная более новая страница имеет пустой список элементов; после syncAll локальный штрих остаётся. Ветка `hasLocalElements && cloudElemCount === 0` при этом отправляет старый штрих обратно в облако.

**Направление исправления:** сохранять в протоколе pageId, версию и факт полного снимка, включая пустой. Применять снимок атомарно только при разрешённой версии или использовать поэлементные tombstone. Не считать пустое облако доказательством, что его надо заполнить локальными остатками.

### A06. Удаления ненадёжны при офлайне, ошибке и перезапуске

**Источник:** `syncEngine.ts:181–191, 320–380`; `supabaseProvider.ts:301–328`; `storage.ts:340–372, 470–522`.

`notifyDelete()` не входит в retry-очередь; при отсутствии userId событие пропускается, при ошибке только логируется. Supabase `deleteItems()` не проверяет возвращённое поле error, поэтому удаление может завершиться для движка успешно при отказе API. Контракт возврата `{ data, error }` показан в [документации Supabase](https://supabase.com/docs/reference/javascript/update).

Локальные tombstone частично позволяют повторить удаления страниц/разделов в syncAll, но аналогичной отправки tombstone блокнота нет. Его облачная активная запись может снова попасть в локальную БД. Restore не обновляет updatedAt, и после потери очереди облачный tombstone имеет приоритет над локальным восстановлением. PULL удаляет страницы/разделы физически, поэтому их локальная корзина больше не работает для этих записей.

**Направление исправления:** персистентная очередь удалений и восстановлений; единая версионная модель tombstone для всех сущностей; обязательная проверка ошибок API; не удалять локальную историю физически в обычном PULL.

### A07. Изображения не входят в облачную синхронизацию и полный бэкап

**Источник:** `storage.ts:535–618`, `assetManager.ts`, оба провайдера; `TextBlockView.tsx:139–151`.

Изображение хранится в таблице assets как Blob; в textBlocks попадает HTML с blob URL и data-asset-id. Ни экспорт/импорт полной базы, ни облачные бандлы не передают assets. На другом устройстве либо после восстановления в чистом браузере нет Blob, из которого можно восстановить URL. Бэкап сохраняет текстовую ссылку, но не само изображение.

**Направление исправления:** версионированный формат бэкапа с бинарными assets, проверкой ссылочной целостности и контрольными суммами; отдельный канал загрузки/скачивания облачных assets с устойчивыми ID. Обратная совместимость со старыми JSON обязательна.

### A08. Импорт может очистить базу по формально допустимому пустому объекту

**Источник:** `storage.ts:579–618`; `ExportModal.tsx:235–243`.

Единственная проверка — существование parsed.data. Файл `{"data":{}}` принимается, все массивы становятся пустыми, после clear всех таблиц транзакция успешно фиксируется. Проверок версии, полей, отношений и полноты бэкапа нет. Экспорт делает несколько независимых чтений и не flush текущие 400-мс изменения редактора; полученная копия может быть несогласованной или без последних правок.

**Направление исправления:** валидировать до изменения БД, сначала сохранять текущие правки и исходную копию; использовать согласованный read-снимок и промежуточное восстановление. Неполный/повреждённый файл должен отклоняться без очистки.

### A09. Очередь синхронизации не привязана к аккаунту и не переживает перезапуск

**Источник:** `syncEngine.ts:46–51, 71–72, 193–267`; `db/idb.ts:55`.

IndexedDB одна для всех аккаунтов данного origin; pendingPayload хранится только в памяти. `setUser()` не очищает/изолирует очередь, а flush использует пользователя, активного в момент отправки. При смене аккаунта локальные данные предыдущего могут отправиться в новый. Текущие in-flight операции тоже не отменяются и не проверяют смену сессии. Это отличается от осознанного переноса гостевых заметок при первом входе.

После перезапуска syncAll пытается восстановить часть отправок по наличию/updatedAt, но существующие переименования блокнотов и разделов не входят в нормальный PUSH существующих активных записей. `savePageDiff()` для изменений элементов и `updatePageMetadata()` не повышают updatedAt страницы: дата страницы не отражает изменение рисунка/текста. Поэтому потерянная RAM-очередь не восстанавливается надёжно сравнением страниц.

**Направление исправления:** durable outbox в той же транзакции, что локальные данные; область userId/provider, отдельные гостевые данные и явный перенос; проверка поколения сессии после await.

### A10. Нет сериализации синка и защиты локальных правок во время PULL

**Источник:** `syncEngine.ts:193–267, 281–593`; `AuthControls.tsx:19–43`.

У flush/syncAll нет общего in-flight lock. setUser запускает flush, сразу после него AuthControls запускает syncAll; таймеры, ручной запуск и visibilitychange создают другие точки входа. Старый запрос может завершиться после нового. В конце syncAll активный холст безусловно перезагружается из БД, независимо от версии и dirty-правок, сделанных пользователем во время ожидания сети. Это риск сбросить ещё не сохранённый ввод.

Локальный debounce 400 мс не имеет обработчика закрытия/скрытия страницы, который сначала сохраняет local dirty. Обработчики beforeunload/visibilitychange существуют только у облачного движка. Гарантия сохранения при завершении вкладки из этого не следует.

**Направление исправления:** один последовательный исполнитель синка; локальные ревизии и защита dirty-полей; только адресное обновление затронутых страниц, без безусловного сброса редактора. Нельзя полагаться на завершение сетевой операции при закрытии вкладки.

### A11. Переименования и старые ссылки теряют slug-метаданные при PULL

**Источник:** оба `pushPages()`/`pullAll()`; `syncEngine.ts:491–503`.

Провайдеры не передают slug/slugAliases. При PULL локальная страница создаётся заново из перечисленных полей без сохранения этих локальных полей. Алиасы старых ссылок и уникальные слаги исчезают; генерация по названию не обеспечивает прежний адрес и защиту от коллизий на другом устройстве.

**Направление исправления:** расширять схему и протокол аддитивно; старые клиенты/данные должны оставаться читаемыми; существующие aliases нельзя уничтожать при обновлении остальных полей.

## P2 и дополнительный backlog

### A12. Тесты не защищают ключевую реализацию синка

`scripts/tests/sync-and-history.test.mjs` во многих сценариях тестирует вручную написанный алгоритм и MockCommandStack. Тесты Smart Diff проверяют условие, которого в текущем syncAll нет: фактически активный холст перезагружается безусловно. Поэтому 49 зелёных тестов не опровергают воспроизведённые выше ошибки.

Нужны проверки настоящего движка с контролируемой сетью/БД, плюс браузерные сценарии. Перечень обязательных сценариев приведён ниже. В репозитории не найден workflow CI; отдельного lint-скрипта нет, но strict tsc включён.

### A13. Риски HTML-ввода и импорта

`TextBlockView.tsx:57,68` устанавливает contentHTML напрямую в innerHTML. Вставка plain text с символом ^ передаёт результат convertPowersToSuperscript в insertHTML; функция сохраняет теги и не является sanitizer. Например, текст с HTML-тегом и 2^2 будет трактоваться как разметка. При импорте недоверенного JSON нет очистки HTML. Названия файлов также интерполируются в HTML-атрибут alt без экранирования.

Это установлено по пути данных; выполнение вредоносного payload в браузере не проверялось. Нужны разделение plain text/HTML, очистка разрешённой rich-text разметки и создание image DOM без строковой интерполяции.

### A14. Невалидный сжатый бандл превращается в пустую страницу без ошибки

`decompressJson()` при ошибке возвращает исходную строку; `decompressBatch()` заменяет отсутствующие массивы на []. Облачный повреждённый пакет становится «успешно распакованным пустым набором». Для будущего корректного применения полных снимков это особенно опасно: пустой снимок и повреждённые данные должны быть различимы. Нужны валидация формата, явная ошибка и сохранение последней исправной локальной версии.

### A15. Supabase pullAll не имеет пагинации

Четыре select('*') возвращают то, что разрешает лимит проекта; range/пагинации нет. Если число записей превысит настроенный предел API, снимок станет неполным. Production-лимит не проверялся. В дальнейшем отсутствие строки в неполном ответе нельзя трактовать как удаление.

### A16. Запуск без Clerk-конфигурации

`main.tsx` допускает App без ClerkProvider, но Header всегда рендерит AuthControls с useUser/useAuth, и CloudSettingsModal вызывает те же hooks. Ветка «нет ключа, локальное приложение» не имеет согласованной реализации. Это риск startup-ошибки в чистой установке; браузерный запуск без ключа отдельно не выполнялся.

### A17. Зависимости и сборка

- source-map-js 1.2.1 находится в цепочке vite → postcss. npm сообщает high DoS advisory. По дереву это инструмент сборки; прямой путь эксплуатации через интерфейс заметок не установлен. [Advisory](https://github.com/advisories/GHSA-68fv-2mgg-jv7q).
- KaTeX 0.16.47: low advisory, обход trust при уже существующем prototype pollution. Это условная проблема, не самостоятельное доказательство XSS приложения. Обновление пересекает диапазон 0.16.x и требует проверки формул. [Advisory](https://github.com/advisories/GHSA-238p-pmpm-9mq7).
- Основной JS 753.90 kB, gzip 214.71 kB. Vite предупреждает о размере >500 kB и смешанном static/dynamic импорте storage. Это задача следующего этапа, не причина менять формат хранения сейчас.

### A18. Перо, текст и большие холсты: отдельный этап

У обработчиков событий холста в просмотренных местах есть симметричная очистка listeners, история ограничена 100 командами, жесты имеют отдельный GestureManager, пространственный индекс используется для выборок. Это положительная основа.

Предмет следующих проверок: реальные стилусы/palm rejection и pointercancel; отмена жеста при потере фокуса; быстрые переходы между страницами при async load; IME, undo contentEditable, каретка, большие таблицы; объём памяти assets и освобождение object URLs. SpatialIndex перебирает все клетки AABB, PNG-экспорт выделяет canvas на весь размер заметки без верхнего предела — крупные координаты/страницы могут создавать чрезмерную нагрузку. Без аппаратного и браузерного профилирования конкретные FPS/лимиты не установлены.

## Безопасный порядок дальнейшей работы

1. **Сначала восстановимость.** Закрыть A01/A03/A07/A08: устранить опасную инициализацию, честно обрабатывать ошибки локального сохранения, подготовить полный бэкап с изображениями и проверенный restore. До любых миграций снять копию всех локальных таблиц и независимую копию облака; восстановить их в отдельной среде и сравнить содержимое.
2. **Зафиксировать инварианты local-first.** Успешный индикатор только после tx.done. Локальные данные и outbox записываются атомарно. Ошибка сети не отменяет локальную запись. Конфликт не уничтожает ни одной версии. Рабочее хранилище нельзя clear при старте или при невалидном ответе.
3. **Укрепить протокол синка.** Durable outbox, последовательный исполнитель, области аккаунт/провайдер, ревизии, tombstone, пустые снимки, assets, slug/aliases, проверка ошибок и полноты облачного ответа. Формат вводить аддитивно, с чтением прежних бандлов и без массового преобразования пользовательской БД на старте.
4. **Проверять на копиях.** Имитировать два устройства и несколько вкладок, запретить destructive PULL до доказанной корректности. Сначала отдельное тестовое облако, затем ограниченное включение после проверки резервных копий. Для отката сохранить прежние данные и совместимость, а не полагаться только на откат JS.
5. **После стабилизации — производительность, перо и текст.** Каждое изменение отдельным проверяемым шагом; оптимизацию не объединять с миграцией данных и исправлением конфликтов.

Обязательные критерии перед включением нового синка:

- старое облако не заменяет новые локальные правки; конфликт сохраняет обе версии;
- изменение/удаление/очистка страницы совпадают на двух устройствах, включая пустую страницу;
- сеть пропадает до/после каждого шага; повторная отправка идемпотентна;
- перезагрузка офлайн сохраняет очередь, переименования, рисунки и удаления;
- ошибка IndexedDB не показывает saved и не теряет dirty;
- восстановление страницы/раздела/блокнота переживает рестарт;
- смена аккаунта/провайдера не отправляет данные не тому владельцу;
- старая и новая схема читаются; повреждённый пакет не считается пустым;
- импорт/экспорт переносят изображения, алиасы, корзину и последние правки;
- редактирование во время долгого PULL и быстрые смены страниц сохраняют введённые данные;
- два параллельных запроса/две вкладки не откатывают состояние поздним ответом;
- объём выше лимита API полностью вычитывается с пагинацией.
