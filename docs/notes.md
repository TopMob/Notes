# Клон Microsoft OneNote — расширенный технический план реализации

## Углублённая проработка: архитектура бесконечного холста и движка рисования

---

## 0. Философия проекта

Ключевая техническая сложность этого проекта — не UI (вкладки, сайдбар, темы это рутина), а **движок бесконечного холста с рукописным вводом**, который должен:

- держать **60 FPS** даже при тысячах штрихов на странице;
- корректно работать с любым источником ввода (мышь, палец, стилус с нажимом и наклоном);
- не блокировать поток рендера тяжёлыми операциями (хит-тестинг ластика, лассо, поиск);
- сохранять данные с минимальной задержкой, не теряя штрихи при закрытии вкладки.

Этот план строится вокруг решения именно этой задачи, остальное — производные детали.

## 2. Модель данных

```typescript
// Единица мира — "World Space", не зависит от масштаба/скролла
interface Point {
  x: number; y: number;
  pressure: number;   // 0..1, из PointerEvent.pressure (0.5 если устройство не даёт давление)
  tiltX?: number; tiltY?: number;
  t: number;           // timestamp, нужен для скорости → влияет на толщину линии
}

interface Stroke {
  id: string;
  tool: 'pen' | 'highlighter';
  points: Point[];              // сырые точки в мировых координатах
  color: string;
  baseWidth: number;
  opacity: number;               // highlighter ≈ 0.35
  blendMode: 'source-over' | 'multiply';
  bounds: AABB;                  // bounding box — кэш для culling/hit-теста
  createdAt: number;
}

interface ShapeObject {
  id: string;
  type: 'line' | 'arrow' | 'rect' | 'ellipse' | 'axis';
  anchor: Point; end: Point;
  style: { color: string; width: number; dashed?: boolean };
}

interface TextBlock {
  id: string;
  x: number; y: number; width: number;    // мировые координаты и ширина (высота — авто)
  contentHTML: string;                     // rich text (bold/italic/lists/checkbox/KaTeX-плейсхолдеры)
  zIndex: number;
}

interface PageCanvasState {
  pageId: string;
  strokes: Stroke[];
  shapes: ShapeObject[];
  textBlocks: TextBlock[];
  camera: { x: number; y: number; zoom: number }; // индивидуальная позиция камеры страницы
  background: 'plain' | 'ruled' | 'grid-small' | 'grid-large';
}
```

Важно: **штрихи хранятся в мировых координатах**, а не в экранных пикселях. Это единственный способ сделать масштаб независимым от истории рисования — при зуме мы не пересчитываем сами данные, а лишь матрицу отображения.

## 3. Система координат бесконечного холста (ключевой раздел)

### 3.1. Два пространства: World Space и Screen Space

- **World Space** — абстрактная бесконечная плоскость $(X_w, Y_w)$, в ней хранятся все объекты страницы. Начало координат $(0,0)$ фиксировано и не двигается.
- **Screen Space** — пиксели видимого `<canvas>` элемента.

Переход между ними описывается матрицей камеры:

```typescript
interface Camera { x: number; y: number; zoom: number; }

function worldToScreen(p: Point, cam: Camera, viewportSize: {w:number;h:number}) {
  return {
    x: (p.x - cam.x) * cam.zoom + viewportSize.w / 2,
    y: (p.y - cam.y) * cam.zoom + viewportSize.h / 2,
  };
}

function screenToWorld(p: {x:number;y:number}, cam: Camera, viewportSize: {w:number;h:number}) {
  return {
    x: (p.x - viewportSize.w / 2) / cam.zoom + cam.x,
    y: (p.y - viewportSize.h / 2) / cam.zoom + cam.y,
  };
}
```

Вместо пересчёта каждой точки вручную в проде используется `CanvasRenderingContext2D.setTransform()` — мы один раз задаём трансформацию контекста перед кадром, а дальше рисуем штрихи в их «родных» мировых координатах, браузер сам проецирует их на экран (GPU-ускоренно):

```typescript
ctx.setTransform(
  cam.zoom * dpr, 0, 0, cam.zoom * dpr,
  (viewportSize.w / 2 - cam.x * cam.zoom) * dpr,
  (viewportSize.h / 2 - cam.y * cam.zoom) * dpr
);
```

`dpr` = `window.devicePixelRatio`, что автоматически решает проблему размытости на Retina/4K: физический размер canvas-буфера ставится `cssWidth * dpr × cssHeight * dpr`, а CSS-размер остаётся `cssWidth × cssHeight`.

### 3.2. Панорамирование (Pan)

Три источника события панорамирования обрабатываются единым `PanZoomTool`:

1. **Пробел + ЛКМ**: `pointerdown` при зажатом `Space` переключает курсор на `grab`, дальше — дельта `pointermove` конвертируется в смещение камеры: `cam.x -= dx / cam.zoom` (делим на zoom, чтобы скорость панорамирования была одинаковой визуально на любом масштабе).
2. **Средняя кнопка мыши** — тот же обработчик, фильтр `event.button === 1`.
3. **Тачпад (жест двумя пальцами)** — обрабатывается через `wheel`-событие с `deltaMode === 0` и без `ctrlKey` (в отличие от pinch-zoom, где `ctrlKey === true` — так браузеры сигнализируют pinch на трекпаде).

Инерция (опционально, для «богатого» ощущения): после `pointerup` считается скорость последних 3–4 кадров, затем применяется decay-анимация (`velocity *= 0.92` каждый кадр, пока `|velocity| > 0.01`).

### 3.3. Масштабирование (Zoom) относительно курсора

Главное требование ТЗ — зум должен «прилипать» к точке курсора, а не к центру экрана. Математика:

```typescript
function zoomAtPoint(cam: Camera, screenPoint: {x:number;y:number}, factor: number, viewportSize) {
  const worldBefore = screenToWorld(screenPoint, cam, viewportSize);
  cam.zoom = clamp(cam.zoom * factor, 0.25, 4.0); // 25%..400%
  const worldAfter = screenToWorld(screenPoint, cam, viewportSize);
  // компенсируем сдвиг, вызванный изменением zoom
  cam.x += worldBefore.x - worldAfter.x;
  cam.y += worldBefore.y - worldAfter.y;
}
```

Триггеры: `wheel` + `ctrlKey` (трекпад pinch и `Ctrl+колесо`), кнопки `+`/`–` в UI (зумят к центру экрана), двойной клик на «100%» — плавный `requestAnimationFrame`-твин обратно к `zoom = 1`.

### 3.4. Бесконечность на практике: тайлинг и spatial index

Технически «бесконечного» холста не существует — есть очень большая условная область (например, ±10 000 000 у.е. по каждой оси, что при разумном зуме практически неотличимо от бесконечности) и **эффективная структура данных**, не позволяющая производительности деградировать с ростом числа штрихов.

**Quadtree** — основная структура:

```typescript
class QuadTreeNode {
  bounds: AABB;
  items: Stroke[] = [];       // до capacity (например, 16) элементов
  children?: [QuadTreeNode, QuadTreeNode, QuadTreeNode, QuadTreeNode];

  insert(stroke: Stroke) { /* рекурсивное разбиение при переполнении */ }
  query(range: AABB): Stroke[] { /* возвращает только штрихи, чей bbox пересекает range */ }
}
```

Применение:
- **Viewport culling** — на каждый кадр вычисляем видимый мировой прямоугольник (`screenToWorld` для 4 углов canvas) и запрашиваем у quadtree только штрихи внутри него + запас 20% (чтобы избежать popping при быстром pan). Не видимые штрихи вообще не передаются в `ctx.stroke()`.
- **Хит-тест ластика** — вместо перебора всех штрихов страницы, `EraserTool` запрашивает у quadtree только штрихи рядом с курсором.
- **Лассо** — финальный point-in-polygon тест применяется только к кандидатам из bbox-запроса region селекции, а не ко всем объектам.

Quadtree перестраивается инкрементально при добавлении/удалении/перемещении штриха (`remove` + `insert`), полный rebuild — только при массовых операциях (импорт, batch-undo).

### 3.5. Многослойная структура рендера

Как и заявлено в базовом плане, используется несколько `<canvas>`, наложенных абсолютным позиционированием друг на друга — это позволяет перерисовывать только то, что реально изменилось:

| Слой | Назначение | Когда перерисовывается |
|---|---|---|
| `background-canvas` | сетка/линейка/клетка | только при смене режима фона, zoom, pan |
| `content-canvas` | все закоммиченные штрихи, фигуры (highlighter рисуется первым в подслое с `globalCompositeOperation = 'multiply'`, поверх — ink-слой) | при коммите нового штриха, undo/redo, pan/zoom (через quadtree-culling — дёшево) |
| `active-stroke-canvas` | **временный** слой — только текущий штрих, который пользователь рисует прямо сейчас | на каждый `pointermove`, 60 раз/сек |
| `selection-overlay-canvas` | рамка лассо, resize-хендлы, bounding box выделения | при взаимодействии с выделением |
| `dom-overlay` (обычный React DOM, не canvas) | текстовые контейнеры — позиционируются через `transform: translate() scale()`, синхронизированную с камерой | React-рендер по изменению camera/content |

Разделение `active-stroke-canvas` от `content-canvas` — критично для производительности: во время рисования перерисовывается **только маленький временный canvas с одним штрихом**, а не вся страница целиком. По `pointerup` штрих «запекается» (bake) в `content-canvas` через `drawImage`, quadtree обновляется, а временный слой очищается.

### 3.6. Рендер-цикл

```typescript
function renderLoop() {
  if (dirtyFlags.background) drawBackground();
  if (dirtyFlags.content) drawVisibleStrokes();   // culling через quadtree
  if (dirtyFlags.activeStroke) drawActiveStroke();
  clearDirtyFlags();
  requestAnimationFrame(renderLoop);
}
```

Рендер управляется dirty-флагами, а не безусловным перерисовыванием каждого кадра — экономит батарею на ноутбуках/планшетах, когда пользователь не взаимодействует с холстом.

## 4. Движок рисования и рукописного ввода

### 4.1. Обработка ввода: Pointer Events

Единый API для мыши/пальца/стилуса — `PointerEvent`. Ключевые поля:

- `pointerType`: `'pen' | 'touch' | 'mouse'` — определяет поведение (например, палец без стилуса может использоваться только для панорамирования/зума в режиме «только стилус рисует», опционально настраивается пользователем — **palm rejection**);
- `pressure`: 0–1 (реальное давление у стилуса; `0.5` — константа для мыши/пальца без поддержки);
- `tiltX/tiltY`: угол наклона пера (используется для имитации «скоса» маркера, опционально);
- `getCoalescedEvents()` — браузер может «схлопнуть» несколько физических событий в одно на медленных кадрах; этот метод возвращает **все** промежуточные точки, что критично для гладкости линии на высокочастотных стилусах (Apple Pencil, Surface Pen дают до 240 событий/сек, а `requestAnimationFrame` — только 60/сек).

```typescript
canvas.addEventListener('pointerdown', (e) => {
  if (currentTool.type === 'pen' || currentTool.type === 'highlighter') {
    canvas.setPointerCapture(e.pointerId);   // не терять события, если курсор уйдёт за пределы canvas
    strokeBuilder.begin(screenToWorld(e, camera, viewport), e.pressure);
  }
});

canvas.addEventListener('pointermove', (e) => {
  const events = e.getCoalescedEvents?.() ?? [e];
  for (const ev of events) {
    strokeBuilder.addPoint(screenToWorld(ev, camera, viewport), ev.pressure, ev.timeStamp);
  }
  markDirty('activeStroke');
});

canvas.addEventListener('pointerup', (e) => {
  const stroke = strokeBuilder.finish();
  commandStack.execute(new AddStrokeCommand(stroke));  // bake + undo entry
});
```

### 4.2. Сглаживание линии: `perfect-freehand`

`perfect-freehand` превращает массив точек `{x, y, pressure}` в **замкнутый полигон** (outline), который затем заливается одним `fill()` — это даёт органичную, каллиграфическую форму линии (тоньше на быстрых движениях, толще на медленных/нажатых), без «ступенек».

```typescript
import { getStroke } from 'perfect-freehand';

const outlinePoints = getStroke(
  points.map(p => [p.x, p.y, p.pressure]),
  {
    size: baseWidth,
    thinning: 0.6,       // насколько сильно давление влияет на толщину
    smoothing: 0.5,       // сглаживание "дрожи" руки
    streamline: 0.5,       // сглаживание траектории в реальном времени
    easing: (t) => t,
    simulatePressure: pointerType !== 'pen',  // для мыши — эмулируем нажим по скорости
  }
);

// outlinePoints → SVG-path или Canvas Path2D через getSvgPathFromStroke()
const path = new Path2D(getSvgPathFromStroke(outlinePoints));
ctx.fillStyle = strokeColor;
ctx.fill(path);
```

Для **маркера (highlighter)**: `thinning: 0`, `opacity: 0.35`, `ctx.globalCompositeOperation = 'multiply'` — это даёт классический эффект «просвечивания» через уже нарисованный текст/чернила, не забивая их плотным цветом.

### 4.3. Жизненный цикл штриха и буферизация точек

1. `pointerdown` → создаётся `StrokeBuilder` с пустым массивом точек в мировых координатах.
2. Каждый `pointermove` добавляет точки (через `getCoalescedEvents`) в буфер. **На каждый кадр** (не на каждое событие — троттлинг через `requestAnimationFrame`) `active-stroke-canvas` полностью очищается и перерисовывается заново вызовом `getStroke()` по всему текущему буферу — это дёшево, пока буфер не рисуется дольше пары секунд.
3. `pointerup` → буфер прогоняется через **Douglas-Peucker упрощение** (`simplify.ts`, epsilon ≈ 0.5–1 world unit) — убирает избыточные точки без потери формы линии, что заметно снижает объём данных на хранение и последующий рендер (перо на 240Hz за 2 секунды даёт ~480 точек, упрощение снижает до ~60–100 без визуальной разницы).
4. Упрощённый штрих регистрируется в `quadtree`, «запекается» в `content-canvas` через `drawImage`, попадает в `CommandStack` как `AddStrokeCommand` (для undo), и асинхронно (debounce ~300 мс) сохраняется в IndexedDB.

### 4.4. Ластик

Два режима, оба используют quadtree для поиска кандидатов рядом с курсором (радиус = размер ластика):

- **Поштриховой (Stroke Eraser)** — фирменная фишка OneNote: при пересечении курсора-круга с bounding box штриха выполняется точный тест «расстояние от курсора до ближайшего сегмента полилинии штриха < радиус ластика»; при попадании штрих целиком удаляется (`RemoveStrokeCommand`, с сохранением в историю для undo).
- **Точечный ластик** — вместо удаления всего штриха, полилиния штриха **разрезается** в точке пересечения с кругом ластика на два новых штриха (или отрезок удаляется, если попадает в середину/край) — реализуется через пересчёт `points[]` с фильтрацией и, при необходимости, split на несколько `Stroke`-объектов.

### 4.5. Лассо-выделение

1. `pointerdown` в режиме Lasso начинает накопление полигона (точки пути движения курсора, тоже мировые координаты, тоже упрощаются Douglas-Peucker после отпускания).
2. `pointerup` замыкает полигон (первая точка соединяется с последней).
3. Quadtree-запрос по bounding box полигона возвращает штрихи-кандидаты.
4. Для каждого кандидата — **point-in-polygon** тест (ray casting algorithm) по каждой точке штриха; штрих считается выделенным, если центр его bbox (или заданный % точек) попадает внутрь полигона.
5. Выделенные штрихи получают общий `SelectionBoundingBox`, отображаемый на `selection-overlay-canvas` с хендлами перемещения/масштабирования/удаления — трансформации применяются как аффинное преобразование ко всем точкам всех выделенных штрихов разом (`MoveSelectionCommand`, `ScaleSelectionCommand` — тоже в истории undo).

### 4.6. Фигуры (Shape Tool)

`pointerdown` → фиксирует anchor-точку, `pointermove` рисует превью на `active-stroke-canvas` (прямая линия/прямоугольник/эллипс от anchor до текущей позиции курсора), `pointerup` коммитит `ShapeObject`. Snapping: при зажатом `Shift` линия защёлкивается на углы кратные 15°, прямоугольник/эллипс — в квадрат/круг.

### 4.7. Undo / Redo

Command pattern — каждое изменение состояния холста (добавление/удаление штриха, перемещение выделения, изменение текстового блока) оборачивается в объект с методами `execute()` / `undo()`:

```typescript
interface Command { execute(): void; undo(): void; }

class CommandStack {
  private undoStack: Command[] = [];
  private redoStack: Command[] = [];

  execute(cmd: Command) {
    cmd.execute();
    this.undoStack.push(cmd);
    this.redoStack = [];               // новая ветка истории обнуляет redo
  }
  undo() { const c = this.undoStack.pop(); if (c) { c.undo(); this.redoStack.push(c); } }
  redo() { const c = this.redoStack.pop(); if (c) { c.execute(); this.undoStack.push(c); } }
}
```

Горячие клавиши `Ctrl+Z` / `Ctrl+Y` (или `Ctrl+Shift+Z`), глубина стека — ограничена (например, 100 операций) во избежание утечки памяти на долгих сессиях.

## 5. Ввод текста и текстовые контейнеры (второй ключевой раздел)

Текстовые блоки — **не** рисуются на canvas, а являются обычными DOM-элементами, позиционированными абсолютно внутри `dom-overlay`, поверх canvas-слоёв. Это осознанный выбор: нативный `contentEditable`/рич-текст-редактор даёт бесплатно курсор, выделение текста, IME для не-латинских раскладок, спелл-чекер браузера и правильную работу с буфером обмена — то, что на голом Canvas пришлось бы реализовывать вручную (как в Google Docs) ценой месяцев работы.

### 5.1. Создание блока: «клик и пиши»

Последовательность событий при клике в свободную область холста:

1. `pointerdown`/`click` на `content-canvas` (не на существующем блоке и не при активном инструменте рисования — активен инструмент `TextCursor`, отдельная кнопка на ленте).
2. Экранные координаты клика конвертируются в мировые (`screenToWorld`), создаётся **черновой** `TextBlock` с пустым `contentHTML`, `width` по умолчанию (например, 240 world units), `zIndex` = максимум среди существующих + 1.
3. Черновик **не пишется в store/IndexedDB сразу** — он живёт в локальном состоянии `DraftTextBlock` до первого символа ввода. Это нужно для пункта 5.5 (авто-удаление пустых блоков).
4. DOM-элемент рендерится в `dom-overlay`, автоматически получает фокус (`ref.current.focus()`), курсор ставится в начало (`Range`/`Selection` API).
5. Как только пользователь вводит первый символ — черновик коммитится как полноценная `Command` (`AddTextBlockCommand`) в `CommandStack` и попадает в debounce-очередь автосохранения.

### 5.2. Синхронизация координат блока с камерой

```typescript
function TextBlockOverlay({ block, camera, viewport }: Props) {
  const screenPos = worldToScreen({ x: block.x, y: block.y }, camera, viewport);
  return (
    <div style={{
      position: 'absolute',
      left: screenPos.x, top: screenPos.y,
      transform: `scale(${camera.zoom})`,
      transformOrigin: 'top left',
      width: block.width,           // ширина в world units, масштабируется вместе с transform
    }}>
      <RichTextEditor block={block} />
    </div>
  );
}
```

Важный нюанс: `contentEditable` при `transform: scale()` иногда даёт браузерам (особенно Safari) неточный расчёт позиции каретки при клике мимо текста. Решение — держать реальный `font-size` блока фиксированным в px и вместо CSS `scale()` на **самом тексте** масштабировать только позицию и внешний контейнер, либо применять `scale()` к родителю, но пересчитывать `font-size = baseFontSize * camera.zoom` напрямую при заходе в режим редактирования, чтобы каретка позиционировалась по реальной геометрии шрифта, а не по трансформированной. Это единственное место в проекте, где чистая матричная трансформация уступает ручному пересчёту ради корректности взаимодействия с нативным DOM-редактированием текста.

### 5.3. Rich-text редактор: выбор технологии и структура

Используется `Tiptap` (обёртка над `ProseMirror`) — даёт готовую модель документа, историю изменений на уровне текста (отдельную от canvas `CommandStack`, но обе интегрированы через общий `Ctrl+Z`, см. 5.7), и расширяемую систему нод/марок.

Набор нод и марок (`extensions`):

| Тип | Расширение Tiptap | Горячая клавиша |
|---|---|---|
| Жирный / курсив / подчёркнутый | `Bold`, `Italic`, `Underline` | `Ctrl+B` / `Ctrl+I` / `Ctrl+U` |
| Заголовки H1/H2/обычный текст | `Heading(level: 1\|2)` + `Paragraph` | `Ctrl+Alt+1/2/0`, либо выпадающий стиль на ленте «Главная» |
| Маркированный / нумерованный список | `BulletList`, `OrderedList` | `Ctrl+Shift+8` / `Ctrl+Shift+7` |
| Чекбокс (To-Do) | кастомная нода `TaskItem` с `input[type=checkbox]` внутри `<li>`, состояние `checked` хранится в атрибутах ноды | `Ctrl+Shift+9` или ввод `[] ` в начале строки (авто-конвертация по паттерну, как markdown shortcuts) |
| Формула KaTeX | кастомная **inline-нода** `MathInline` (см. 5.4) | `$…$` авто-детект по завершающему `$` |

### 5.4. Ввод и рендер формул KaTeX

Формулы — не просто текст в разметке, а **отдельная неделимая inline-нода** документа Tiptap (аналогично тому, как изображение — атомарный узел). Поток ввода:

1. Пользователь печатает `$` — редактор переключается в режим «сырого LaTeX», показывая моноширинный текст без рендера (courier-стиль, чтобы визуально отличался от обычного текста).
2. Ввод продолжается: `$X_2 = \frac{-4}{-4} = 1$`. Плагин Tiptap (`InputRule`) отслеживает паттерн `/\$([^$]+)\$/` — как только пользователь вводит закрывающий `$`, диапазон между парой `$…$` заменяется на атомарную ноду `MathInline` с атрибутом `latex: string`.
3. Нода рендерится через `katex.renderToString(latex, { throwOnError: false })` в `dangerouslySetInnerHTML` внутри `NodeView` — при синтаксической ошибке KaTeX ноды подсвечиваются красным контуром вместо падения всего редактора (`throwOnError: false` обязателен).
4. **Редактирование существующей формулы**: клик по отрендеренной ноде переключает именно её обратно в сырой LaTeX-режим (аналогично двойному клику на формулу в OneNote/Word), остальной текст блока остаётся в обычном режиме — реализуется через `NodeView` с внутренним `isEditing` состоянием и `contentEditable=false` на самой ноде, но с вложенным `<input>` для правки latex-строки.
5. **Блочные формулы** (`$$…$$`, матрицы, системы уравнений методом Гаусса) — отдельная **block-level нода** `MathBlock`, центрированная, с собственной строкой, а не инлайн — паттерн триггерится по `$$` в начале строки.

Матрицы вводятся стандартным KaTeX/LaTeX синтаксисом (`\begin{pmatrix} a & b \\ c & d \end{pmatrix}`), пользователю в UI предлагается кнопка-подсказка «Вставить матрицу» на ленте «Вставка», которая просто вставляет шаблон-заготовку с плейсхолдерами, готовую для правки.

### 5.5. Границы блока, ресайз и авто-удаление

- **Drag-handle** (серая полоса сверху): `pointerdown` на хендле переключает блок в режим перетаскивания; дельта экранных координат конвертируется в мировые (`dx / camera.zoom`, `dy / camera.zoom`) и прибавляется к `block.x/y` на каждый `pointermove`; финальная позиция коммитится как `MoveTextBlockCommand` по `pointerup` (не на каждый кадр — иначе undo-стек забивается сотнями микро-шагов).
- **Resize-handle** (правый край): аналогично, но меняет `block.width`; высота блока всегда `auto` (определяется содержимым через обычный CSS-поток), что соответствует поведению OneNote.
- **Авто-удаление пустого блока**: при `blur` (потере фокуса) редактор проверяет `block.contentHTML` на пустоту (после strip тегов/пробелов); если пусто и блок остаётся черновиком (см. 5.1) — DOM-элемент размонтируется без записи в store; если это уже существующий (ранее сохранённый и потом полностью очищенный пользователем) блок — выполняется `RemoveTextBlockCommand` через `CommandStack` (чтобы удаление тоже попадало в Undo).

### 5.6. Навигация и взаимодействие с холстом

- `Tab` / `Shift+Tab` внутри списка — стандартное изменение уровня вложенности (delegated в Tiptap `List` extension).
- Клик **вне** активного текстового блока снимает с него фокус (`blur`) и, если инструмент рисования не активен, а клик пришёлся на пустую область — создаёт новый блок (см. 5.1); клик на уже существующий блок — переводит фокус в него, ставя каретку в позицию клика (нативное поведение `contentEditable`).
- Если активен инструмент рисования (Pen/Highlighter) — клик по существующему текстовому блоку **не** открывает редактирование: пользователь может обвести/подчеркнуть текст ручкой поверх блока, штрих и текстовый DOM-элемент визуально накладываются (штрих на `content-canvas`, блок в `dom-overlay` — z-порядок регулируется CSS `z-index`, обычно текст ниже, чернила поверх, но настраивается пользователем через контекстное меню блока «На передний/задний план»).
- Лассо-выделение затрагивает **и штрихи, и текстовые блоки**: если полигон лассо пересекает bounding box текстового блока (получаем через `getBoundingClientRect` → в мировые координаты), блок добавляется в общее выделение и может перемещаться вместе со штрихами одним жестом.

### 5.7. Undo/Redo для текста

Два независимых, но синхронизированных источника истории:

- **Canvas `CommandStack`** — операции уровня блока целиком: создание, удаление, перемещение, ресайз текстового блока.
- **Tiptap/ProseMirror history** — операции уровня символов внутри одного блока (встроенный плагин `history` у ProseMirror, отдельный стек на каждый активный редактор).

Глобальный `Ctrl+Z` сначала проверяет, находится ли фокус внутри активного текстового редактора: если да — событие делегируется в ProseMirror `undo()` (откат последнего символьного изменения); если фокус на холсте — событие обрабатывается canvas `CommandStack` (откат последнего штриха/перемещения/удаления блока). Такое разделение соответствует ожидаемому поведению пользователя: находясь внутри текста, `Ctrl+Z` должен откатывать текст посимвольно, а не «телепортировать» весь блок.

### 5.8. Вставка изображений и вложений внутрь текста

Кнопка «Вставить → Изображение» на ленте открывает файловый диалог (`<input type="file" accept="image/*">`), выбранный файл конвертируется в `Blob`, сохраняется в отдельной таблице IndexedDB (`attachments: { id, blob, mimeType }`, не инлайнится как base64 в `contentHTML` — это раздувало бы размер текстовых записей), в текст вставляется Tiptap-нода `ImageBlock` с `attachmentId`-ссылкой; при рендере нода создаёт `URL.createObjectURL(blob)` и освобождает его (`revokeObjectURL`) при размонтировании ноды во избежание утечек памяти.

## 6. Хранилище данных

### 6.1. Схема IndexedDB (`idb`)

```
DB: onenote-clone (v1)
├── notebooks     { id, title, createdAt, order }
├── sections      { id, notebookId, title, color, order }
├── pages         { id, sectionId, title, createdAt, order, camera, background }
├── strokes       { id, pageId, tool, points, color, width, opacity, blendMode, bounds }  — индекс по pageId + bounds (для потенциальной частичной подгрузки)
├── shapes        { id, pageId, ... }
└── textBlocks    { id, pageId, x, y, width, contentHTML, zIndex }
```

Индекс `pageId` на всех таблицах контента — при открытии страницы подгружается только её собственный набор объектов, а не вся база (важно при сотнях страниц).

### 6.2. Автосохранение

- Каждая `Command` после `execute()` ставит операцию в **debounce-очередь** (300–500 мс простоя ⇒ запись в IndexedDB), чтобы не писать на диск при каждом `pointermove`.
- Индикатор «Сохранено / Сохранение…» в шапке отражает состояние очереди.
- `beforeunload` — принудительный синхронный flush очереди при закрытии вкладки.

### 6.3. Экспорт/импорт

- **JSON** — полная сериализация IndexedDB (резервная копия / перенос между устройствами вручную).
- **PNG** — рендер `content-canvas` + `background-canvas` + snapshot текстовых блоков (через `html-to-image` или ручную отрисовку текста на offscreen canvas) в один `drawImage`-композит, обрезанный по bounding box всех объектов страницы (не по видимой области экрана).
- **PDF** — через `pdf-lib` или `jsPDF`, с постраничной разбивкой контента, если bounding box страницы больше формата A4/Letter.

**Этап 5 — Текстовые контейнеры и форматирование (1 неделя)**

## 9. Целевые метрики производительности

- **60 FPS** при рисовании и панорамировании страницы с до 5000 видимых штрихов.
- Задержка «перо → видимый штрих» (input latency) — **< 16 мс** (укладываемся в один кадр).
- Время открытия страницы с 1000+ объектами — **< 200 мс** до первого кадра.
- Автосохранение не должно создавать заметных фризов (запись в IndexedDB — асинхронная, вне главного потока рендера по возможности через `requestIdleCallback`).

## 10. Основные технические риски

| Риск | Митигация |
|---|---|
| Просадка FPS на очень «плотных» страницах (тысячи штрихов) | Quadtree culling + периодическая «сборка мусора» — слияние близких мелких штрихов в растровый тайл (rasterize-to-bitmap для штрихов вне текущего viewport, которые давно не редактировались) |
| Рассинхронизация DOM text-overlay и canvas при быстром zoom/pan | Единый источник истины — `camera` в Zustand, оба слоя подписаны на один и тот же стор, рендерятся в одном `requestAnimationFrame` тике |
| Потеря данных при крахе вкладки | Debounce-запись в IndexedDB + `beforeunload` flush + опциональный `BroadcastChannel` для синхронизации между вкладками одного блокнота |
| Разное поведение `pressure`/`tilt` у разных стилусов/браузеров | Fallback на `simulatePressure` в perfect-freehand при `pressure === 0.5` (признак отсутствия реальных данных о нажиме) |
