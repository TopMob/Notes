# Этап 0: независимое резервирование

Инструменты не импортируют `src/db/storage.ts`, не вызывают `initStorage()` и не запускают облачный синк. Production-приложение не изменено. Их задача — снять исходную информацию до исправлений.

## Что уже проверено

На изолированных тестовых данных выполнен полный цикл IndexedDB → JSON с бинарными assets → новая временная IndexedDB → сравнение контрольных сумм. Открыты восстановленные текст, рисунок и PNG; сохранены корзина и старые aliases. Исходная БД не изменилась. Проверены отсутствие БД, повреждённый архив, запрет восстановления в рабочую/существующую базу и сохранение типов.

Для Turso проверен цикл настоящего libSQL → снимок → новый локальный SQLite → сравнение manifest. Production-выгрузка использует только read-транзакцию и SELECT. Это проверка инструмента, не копия данных пользователя и не проверка прав production-токена.

## Рабочая локальная копия

1. Использовать именно тот браузер, профиль и origin (протокол + домен + порт), где хранятся заметки. Новый браузер/localhost не имеет доступа к прежней IndexedDB.
2. Не открывать/не перезагружать приложение специально ради бэкапа, пока опасная ветка инициализации не устранена. Если приложение уже открыто — прекратить ввод и проверить завершение локального сохранения. Этот инструмент не вызывает flush приложения: его текущая реализация может терять dirty при ошибке.
3. В DevTools Console существующей вкладки выполнить проверенный файл `scripts/stage0/backup-console.js`. Он только устанавливает API `NotesStage0`; сам по себе ничего не читает и не пишет. Исходник генерируется командой `node scripts/stage0/build-console.mjs`.
4. Выполнить `await NotesStage0.downloadIndexedDB()`. Сохранить скачанный JSON вне браузера/репозитория. Вызов читает все существующие object stores одной readonly-транзакцией, включая неизвестные будущие таблицы. Если встречается неподдерживаемый тип, экспорт завершится ошибкой вместо молчаливого пропуска.
5. Архив включает только уже записанное в IndexedDB. Не сохранённые правки в RAM в него не входят; это явно указано в source.inMemoryEditsIncluded. Одна transaction обеспечивает согласованный снимок, но другие вкладки могут продолжить работу после его получения.
6. Проверить файл: `node scripts/stage0/verify-backup.mjs <путь-к-JSON>`. Manifest содержит ключи/ID, counts, SHA-256 записей, схем, бинарных assets и всего содержимого. Проверка связей сообщает об исходных пропусках, не «лечит» их и не удаляет записи.
7. В отдельном тестовом профиле или на отдельном тестовом origin загрузить API инструмента и прочитать этот же файл локальным file picker. Вызвать `await NotesStage0.restoreTemporary(snapshot)`, где snapshot — распарсенный JSON. Функция разрешает только новый `notes_stage0_restore_*`, не перезаписывает рабочее хранилище и повторно читает восстановленное содержимое для сравнения hash.

Обычный импорт приложения не использовать для проверки этого формата. Восстановление stage0 — только в новую временную БД. Blob/object URL восстанавливаются из бинарных данных; старые blob URL в HTML не являются резервной копией изображения.

## Turso

Настроить `TURSO_DATABASE_URL` и `TURSO_AUTH_TOKEN` приватно в окружении. Допустимы соответствующие старые VITE_* переменные; инструмент не читает токены из аргументов и не выводит raw ошибки сервера. Не вставлять секреты в чат.

```text
node scripts/stage0/cloud-backup.mjs --out <НОВАЯ-папка-вне-репозитория>
node scripts/stage0/verify-backup.mjs <папка>/turso-snapshot.json
node scripts/stage0/restore-turso-temporary.mjs --snapshot <папка>/turso-snapshot.json --out <папка>/notes-stage0-restore-check.sqlite
```

Если сеть использует уже настроенные HTTP_PROXY/HTTPS_PROXY, для Node 24 запустить команду с `node --use-env-proxy ...`. TLS-проверку не отключать. В текущей среде обычный fetch Turso дал connect timeout, а штатное применение существующего прокси позволило снять снимок.

Снимок включает существующие Notes-таблицы, raw бандлы без перепаковки, записи всех видимых владельцев/корзины и их SQL-определения. Запись разрешена только в новый локальный файл для проверки restore; в remote-базу этот инструмент ничего не восстанавливает. Копия отражает данные, видимые выданному credential, а не гарантированно все данные проекта. Права токена устанавливаются отдельно в панели управления; запись для проверки прав запрещена. Restore поддерживает таблицы и индексы; необычные определения (например triggers) отклоняются для отдельного рассмотрения.

## Supabase

Для независимого согласованного снимка подготовлен `supabase-backup.mjs`: он вызывает PostgreSQL `pg_dump`, затем readonly SQL-инспекцию RLS/policies/grants. Требуются установленные совместимые `pg_dump`/`psql` и приватно настроенные PGHOST/PGDATABASE/PGUSER, аутентификация через PGPASSWORD или стандартный password file. Инструмент не передаёт пароль/URI в аргументах и не запрашивает интерактивный пароль.

```text
node scripts/stage0/supabase-backup.mjs --out <НОВАЯ-папка-вне-репозитория>
```

Создаётся custom dump схемы public и manifest с hash файлов. `restoreVerified:false` меняется в отчёте только после отдельного восстановления в новый тестовый Postgres и сравнения counts/содержимого/связей. В рабочую БД pg_restore не запускать. Этот путь не резервирует database roles, другие схемы и бинарные объекты Supabase Storage; если они используются, нужны отдельные выгрузки. В текущем коде изображения лежат в локальной assets, поэтому локальная копия обязательна независимо от cloud dump. Папка без manifest означает незавершённую выгрузку.

Один REST select через anon key не является полной независимой копией проекта или проверкой его RLS.

## Репозиторий и повторные проверки

```text
node scripts/stage0/capture-baseline.mjs --out <НОВАЯ-папка>
git bundle create <папка>/repository.bundle HEAD
git bundle verify <папка>/repository.bundle
node --test scripts/stage0/test-backup.test.mjs
```

Baseline сохраняет commit, локальные версии прямых зависимостей, package-lock, исходные схемы и их SHA-256. Версия локальной/облачной схемы из исходников отмечена как ожидаемая, не фактически прочитанная production-схема. Git bundle содержит историю HEAD; текущие незакоммиченные инструменты надо копировать отдельно.

`test-browser-roundtrip.mjs` требует отдельный Playwright и тестовый Chromium. Указать STAGE0_PLAYWRIGHT_MODULE, PLAYWRIGHT_BROWSERS_PATH и новую STAGE0_TEST_OUTPUT. Тест создаёт новый headless browser context; рабочие профили не используются. В package.json приложения новые runtime-зависимости не добавлены.

Копии с пользовательским содержимым хранить вне Git и не публиковать. SHA-256 обнаруживает случайное повреждение, но не доказывает доверенность файла от постороннего источника. Данная версия экспортирует снимок в память и JSON/base64; очень большая БД потребует потокового архиватора, а свободный диск и завершение выгрузки нужно проверить до миграции.

Таблицы с autoIncrement снимаются, но автоматическое восстановление такого снимка отклоняется: readonly-экспорт не может прочитать внутреннее значение генератора удалённых ключей. В текущей схеме Notes autoIncrement не используется. Неизвестные Map/Set/циклические объекты и другие неподдерживаемые типы нельзя считать успешно сохранёнными этим форматом.
